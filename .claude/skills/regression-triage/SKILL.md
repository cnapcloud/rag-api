# Regression Triage — 실패 분류 + 기록

목적: "구현이 끝난 뒤"(validate 검증, PR 드라이런 병합, PR CI) 어느 시점에서 발견되든
같은 방식으로 분류하고 같은 곳에 기록해, `/spec-implement`·`/spec-design`의 재개 로직이
어디서 왔든 일관되게 집어낼 수 있게 한다.

**기준 구현**: `/spec-validate`(`.claude/commands/spec-validate.md` + `validator`
서브에이전트)가 이 절차의 레퍼런스다. 분류 기준이 헷갈리면 거기를 먼저 본다.

## 분류 — 세 목록 중 하나

1. **[설계] 실패** — 레이어/아키텍처 전제가 깨졌거나 design.md의 결정 자체가 잘못된
   경우(역방향 참조, 다른 spec/main과의 설계 충돌 등). 항목: 위치(AC ID 또는 파일:줄) +
   이유.
2. **[구현] 실패 — Task 되돌림 대상** — 실패 위치가 task.md "완료 기준 커버리지"
   표(AC 매핑) 또는 각 Task의 "관련 파일"(파일 경로 매핑)로 특정 Task에 연결되는 경우.
   항목: Task ID + 근거(AC ID 또는 검사명+위치) + 이유.
3. **매핑 없는 실패** — 위 매핑이 하나도 안 되는 경우(spec 범위 밖 코드에서 난 회귀 등).
   항목: 검사명(또는 발생 맥락) + 실패 위치 + 이유.

같은 실패가 여러 항목에 걸치면(예: 여러 파일에서 실패) 위치별로 나눠 각각 분류한다.

## 기록 위치 (spec 폴더의 `implementation.md`)

- **[설계] 실패** — "Task 현황"은 건드리지 않는다. "진행 기록"에도 남기지 않는다 —
  설계를 다시 해야 하므로 이 파일이 아니라 designer가 다시 볼 design.md/task.md 쪽
  문제다.
- **[구현] 실패(매핑됨)** — 해당 Task를 "Task 현황"에서 `done` → `blocked`로 되돌리고,
  "진행 기록"에 `blocked` 블록(근거, 유형 `[구현]`, 이유) append.
- **매핑 없는 실패** — "외부 이상 징후"에 항목(검사, 실패 위치, 이유) append. "Task
  현황"은 건드리지 않는다.

## `index.md` 갱신

세 목록 중 하나라도 항목이 있으면 해당 spec 행 Status를 `blocked`로 갱신한다(이미
`blocked`면 중복 갱신 안 함). 세 목록이 모두 비어야 다음 단계(`validated` 전환 또는
PR 진행)로 넘어간다.

## 사용자 안내

- **[설계] 실패**가 있으면 목록/이유를 전달하고 `/spec-design` 재실행을 안내.
- **[구현] 실패(매핑됨)**가 있으면 목록/이유를 전달하고 `/spec-implement` 재실행을
  안내.
- **매핑 없는 실패**만 있으면 spec 범위 밖 이슈임을 알린다. 실제로 고칠지는
  `/spec-implement`가 재실행될 때 그 커맨드가 사용자에게 물어본다(이 스킬은 기록만
  담당 — 되돌리기/질문 흐름은 각 커맨드 몫).

## 이 스킬을 쓰는 곳

- **`/spec-validate`**(기준) — `validator`가 AC 검증 + 전체 회귀 검증(`make test`/
  `lint`/`typecheck`)으로 찾은 실패를 이 분류로 반환하고, 커맨드가 위 기록/안내를
  수행한다.
- **`/spec-pr` PR 생성 경로** — main에 대한 드라이런 병합 상태에서 돌린 전체 테스트
  스위트 실패를 이 분류로 정리한다.
- **`/spec-pr` merge 확인 경로** — GitHub PR CI 체크 실패(`FAILURE`/`ERROR`)를 이
  분류로 정리한다. CI 로그는 파일:줄이 없을 수 있으니 실패 텍스트/스택트레이스 선에서
  매핑을 판단한다.
