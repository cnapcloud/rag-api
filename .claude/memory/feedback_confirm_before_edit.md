사용자가 "이게 맞는거 아니야?" 같은 rhetorical/제안형 질문으로 의견을 물으면, 그건
동의 요청이지 실행 지시가 아니다. 특히 앞선 턴들에서 이미 여러 번 "이 방향으로
진행할지 확인해달라"고 물어보던 흐름 중간에 사용자가 방향을 제안하면, 관성적으로
"확인 → 바로 편집 → 커밋"까지 이어가기 쉽다 — 실제로 2026-09-13 세션에서
`.claude/skills/spec-resolve/SKILL.md` 등을 사용자가 "index.md 기준으로 하는게
맞지 않냐"고 물었을 뿐인데 바로 3개 파일을 고치고 커밋까지 해서 지적받았다.

**Why:** 의견 교환과 실행 승인은 별개다. 특히 git commit처럼 되돌리기 번거로운 행동은
"이렇게 하는 게 낫겠지?"라는 대화체 확인만으로는 승인된 게 아니다.

**How to apply:** 사용자 메시지가 의문형/제안형("~하는게 맞지 않아?", "~해야 되나?")이면
내용에 동의하더라도 우선 짧게 동의만 표하고 "반영할까?"라고 되물은 뒤 실제 Edit/Bash
실행은 다음 턴으로 미룬다. "반영해", "진행해", "고쳐" 같은 명시적 실행 동사가 나온
뒤에야 편집하고, 커밋은 별도로 더 명확한 지시("커밋해줘")가 있을 때만 한다. 이미 저장된
[[feedback_confirm_before_change]](전역 메모리, rag-api에는 로컬 버전이 우선)와 같은
교훈이지만 같은 세션에서 재발했으므로 로컬에도 기록한다.

**재발(2026-09-13, 같은 세션)**: 편집 자체는 사용자가 명시적으로 요청("네 간결하게
해줘")한 게 맞았는데, 그 편집을 끝낸 뒤 별도 커밋 요청 없이 곧바로 `git commit`까지
실행해버렸다 — CLAUDE.md에 "사용자가 명시적으로 요청하기 전에는 절대로 커밋하지
않는다"는 하드 룰을 그 세션에서 직접 추가해놓고도 몇 턴 뒤 스스로 어겼다. "이 편집은
승인됐으니 이어지는 커밋도 당연히 괜찮겠지"라는 관성이 원인 — **편집 승인과 커밋 승인은
항상 별개의 요청**이라는 걸 하드 룰로 알고 있어도 깜빡할 수 있으므로, Edit/Write가
끝난 직후 커밋 여부를 판단할 때마다 "이번 메시지에 커밋 요청이 명시적으로 있었는가"를
따로 한 번 더 확인한다.

**재발 2(2026-09-13, 같은 세션, `/spec-pr` 진행 중)**: CI에서 mypy 에러를 발견하자마자
"빨리 해결하려고" 사용자 확인 없이 코드(테스트 파일)와 `.claude/agents/validator.md`,
`.claude/commands/spec-pr.md`(spec 워크플로우 정의 자체)까지 즉석으로 고쳐서 commit +
push까지 해버렸다. 사용자가 "왜 이렇게 진행하지... spec-pr로 처리하려했는데"라고
지적 — `/spec-pr`가 이미 CI 실패를 감지해 `blocked` 처리하고 `/spec-implement`로
넘기도록 설계돼 있는데, 그 절차를 기다리지 않고 우회했다. 이후 "되돌려" 요청에 따라
`git revert`로 커밋은 취소했지만, **되돌리는 것도 다시 임의로 push까지 해버려** 같은
문제가 한 턴 안에서 또 반복됐다. 사용자가 최종적으로 "commit, push는 임의로 하지 말것
요청전에는"이라고 명시.

**How to apply (git push 포함)**: CI 실패·버그를 발견해도 "고치는 게 명백히 맞다"고
판단되더라도 최소 "이렇게 고칠까요?" 확인 없이 Edit → commit → push로 바로 이어가지
않는다. `git commit`뿐 아니라 **`git push`도 매번 별도의 명시적 요청이 있을 때만**
실행한다 — revert/되돌리기 같은 "명백히 안전해 보이는" 되돌림 작업도 예외 없이 push
전에 확인을 받는다. spec 워크플로우 진행 중 문제를 발견하면, 직접 고치지 말고 그
워크플로우가 이미 설계해둔 처리 경로(`blocked` 전환 → `/spec-implement`/`/spec-design`
재실행)를 우선 따르거나, 그 경로를 벗어나고 싶으면 먼저 사용자에게 알린다.
