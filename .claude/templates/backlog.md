## 요청 원문

사용자가 실제로 요청한 내용을 요약 없이 그대로/근접하게 남긴다. designer/implementer가
나중에 "왜 이렇게 정리됐는지" 원문과 대조할 수 있어야 한다.

## 목적

이 작업이 왜 필요한지, 어떤 문제를 해결하는지 1~3문장. 구현 방법(how)은 쓰지 않는다 —
그건 plan.md/task.md 몫.

## 세부 기능 및 완료 기준

요청을 세부 기능(F1, F2, ...) 단위로 쪼갠다. "범위"를 뭉뚱그려 나열하지 않고, 각 세부 기능마다
그 기능이 됐는지 확인할 완료 기준을 바로 옆에 둔다 — 범위와 완료 기준이 따로 놀면 "이 항목을
만들었는지 뭘로 확인하는지"가 불명확해진다. "무엇을 바꾸는지"까지만 — 파일/함수 단위 구체
사항은 plan.md에 둔다. 완료 기준 체크박스는 validator만 갱신한다.

각 완료 기준(AC, Acceptance Criteria — 이 문서에서 "완료 기준"과 같은 뜻으로 쓰는 약어다)에는
`F<세부기능번호>-<순번>` 형태의 ID를 붙인다 (예: `F1-1`, `F1-2`,
`F2-1`). designer가 plan.md/task.md에서, validator가 검증 시 이 ID를 그대로 참조하므로
한 번 붙인 ID는 이후 수정 중에도 재번호를 매기지 않는다 — 중간 AC를 지우면 번호에
구멍이 남아도 그대로 둔다.

## 승인

- [ ] 사용자 승인 완료

승인 전에는 이 폴더 아래 어떤 산출물(plan.md 등)도 생성하지 않는다. 이 체크박스는
analyst/designer가 스스로 체크할 수 없다 — 사용자 확인 후 메인 세션이 직접 갱신한다.

**작성 규칙 (analyst 전용)**

- 이 문서는 analyst만 쓴다 — designer/implementer는 이 파일을 갱신하지 않는다
  (완료 기준·승인 체크박스는 예외, 각각 validator/메인 세션이 갱신).
- 아키텍처/스키마 문서와 모순되면 이 템플릿을 채우기 전에 먼저 사용자에게 보고한다.
- 완료 기준 작성이 끝나면 designer에게 그대로 넘긴다 — "어떻게 구현할지"는 절대 미리 적지 않는다.
