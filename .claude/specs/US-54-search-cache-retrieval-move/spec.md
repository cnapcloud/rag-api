# US-54: 검색 캐시 설정을 retrieval 하위로 이동 + 개명

> 담당: `analyst` · spec 워크플로우 1단계 · 템플릿: `.claude/templates/spec.md`
> 상태는 `.claude/specs/index.md`에서만 관리한다(이 파일엔 별도 상태 필드를 두지 않는다).

> 설계: [검색 응답 캐싱 US-53 design.md](../US-53-search-cache/design.md) (검색 캐시 설정 원 설계 — 이번 spec은 그 필드 위치·이름만 옮긴다)

## 요청 원문

"search_cache: 로 되어 있는 설정을 아래처럼 retrieval 하위의 cache로 옮기고 이름도
바꾼다.

```
retrieval:
  cache:
     enabled: false
     ttl_seconds: 3600
     max_entries: 1000
     match_mode: "exact"
     semantic_threshold: 0.95
```

settings.example.yaml, settings.yaml, docker/settings.yaml 세 파일 모두 이 구조로
반영한다."

배경: US-53에서 검색 캐시 설정을 설정 최상위 형제 필드로 추가했는데, 개념적으로는
검색(retrieval)에 종속된 설정이라 다른 검색 하위 설정들처럼 검색 설정 구조 하위로
재배치하는 게 맞다는 판단이 나왔다(위 요청은 그 결론 + 필드명을 `cache`로 축약하는
것까지 포함). 값과 동작은 그대로, 위치와 이름만 바뀌는 순수 리팩터다. US-53은 이미
done으로 History에 있어 그 안에서 고치지 않고 이 새 spec(US-54)으로 스키마 위치/이름만
옮긴다.

## 목적

검색 캐시 설정은 개념적으로 검색(retrieval)에 종속된 설정인데 설정 구조 최상위 형제
필드로 배치돼 있다. 다른 검색 하위 설정들처럼 검색 설정 구조 하위로 중첩시키고 필드명도
`cache`로 축약해, 설정 스키마의 개념적 일관성을 맞춘다.

## 세부 기능 및 완료 기준

### F1. 검색 캐시 설정을 검색 설정 하위 `cache` 필드로 이동+개명

설정 이동 후에도 기존 오버라이드 제한이 그대로 유지된다.

- [x] **F1-1**: 설정 최상위에 검색 캐시 설정 필드가 더는 존재하지 않고, 검색 설정 하위에
  `cache` 필드가 존재하며 기존 5개 항목(`enabled`/`ttl_seconds`/`max_entries`/
  `match_mode`/`semantic_threshold`)과 그 기본값이 그대로 유지된다 (테스트: 단위 테스트).
- [x] **F1-2**: `cache`의 5개 항목 모두 KB별 설정 오버라이드 대상이 아니다 — 이동 전과
  동일하게 오버라이드 시도가 거부된다 (테스트: 단위 테스트로 5개 항목 전부 확인).
- [x] **F1-3**: KB 설정 스키마 조회 응답에서 `retrieval.cache.*` 5개 항목 모두
  오버라이드 불가로 나타난다 (테스트: 단위 테스트).

### F2. 배포용 설정 파일 3종 갱신

세 설정 파일 모두 최상위 `search_cache:` 블록을 `retrieval:` 하위 `cache:` 자식
블록으로 옮긴다(값 자체는 변경하지 않는다).

- [x] **F2-1**: 요청 원문에 명시된 배포용 설정 파일 3종 각각에서 top-level
  `search_cache:` 키가 사라지고, `retrieval:` 블록의 자식으로 `cache:` 블록(요청 원문의
  구조와 동일)이 존재한다 (수동 확인: 세 파일 diff).
- [x] **F2-2**: 세 설정 파일 각각을 로드하면 이동 전과 동일한 `enabled`/`ttl_seconds`/
  `max_entries`/`match_mode`/`semantic_threshold` 값이 새 위치에서 읽힌다 (테스트 또는
  수동 확인).

### F3. 검색 캐시 설정을 참조하는 동작이 이동 후에도 동일하게 유지

검색 캐시 설정을 참조하는 요청 처리 동작 전반이 필드 위치 변경 후에도 그대로 동작한다.

- [x] **F3-1**: 검색 응답에 캐시 적중/미적중 상태가 표시되는 동작과 캐시 삭제 동작이
  설정 위치 변경 이전과 동일하게 유지된다 (테스트: 관련 통합 테스트 전체 통과).

### 공통 완료 기준

- [x] **C1**: 데이터 스키마 관련 설계 문서를 재검토한다. 조사 결과 이 문서는 이번 이동
  대상인 설정 필드 위치를 직접 언급하지 않는다 — 그대로면 변경 불필요, 만약 필드 위치
  언급이 발견되면 새 위치로 갱신한다 (수동 확인).
- [x] **C2**: "검색 설정 하위 항목 중 KB별 오버라이드가 열려 있는 건 한 항목뿐"이라는
  기존 서술이 이동 후에도 참으로 유지된다(F1-2가 이를 보장) — F1-3에서 추가하는 테스트
  케이스로 함께 확인한다.
- [x] **C3**: 검색 캐시 설정 관련 단위/통합 테스트 전체가 필드 위치 변경 후 그린이다
  (테스트: 관련 테스트 전체 실행).

## 비범위

- 검색 캐시 설정의 필드 이름/기본값/검증 로직 자체 변경 — US-53에서 이미 확정된 내용이며
  이번 spec은 위치·필드명 이동만 다룬다.
- 내부 구현상의 클래스/모듈 명명 변경 여부 — 요청 원문은 YAML/필드 위치만 명시했다.
  이 spec은 내부 명명을 강제하지 않는다(design.md에서 결정) — "오픈 이슈" 참고.
- 캐시 저장소의 키 네이밍 체계 변경 — 대상 아님.
- KB별 `cache` 오버라이드를 실제로 여는 것(F1-2로 닫아 기존과 동일하게 유지) —
  필요해지면 별도 US로 분리한다.
- 동명이인 개념(검색 캐시 조회/삭제 로직 모듈)을 사용하는 다른 기능(문서 삭제/상태 조회
  등)의 코드 변경 — 이번 설정 위치 이동과 무관해 대상이 아니다.
