# US-55: 검색 캐시 lookup/store 데코레이터 통합 + 캐시 게이트 훅(set_cache_gate) 추가

> 담당: `analyst` · spec 워크플로우 1단계 · 템플릿: `.claude/templates/spec.md`
> 상태는 `.claude/specs/index.md`에서만 관리한다(이 파일엔 별도 상태 필드를 두지 않는다).

## 요청 원문

검색 캐시 lookup/store를 데코레이터로 통합하고, 외부(rag-ent-api 등)에서 kb_ids 기반
캐시 사용 여부를 판단할 수 있도록 search_cache 모듈에 캐시 게이트 훅(set_cache_gate)을
추가한다. 훅이 없으면 기존 동작과 완전히 동일하다.

배경: rag-ent-api(별도 프로젝트, sibling repo)가 rag-api의 검색 함수를 in-process로 직접
호출해서 쓰는데, rag-ent-api는 KB마다 public/private 구분이 있고(rag-api 자체에는 이
개념이 없음) private KB가 하나라도 섞인 검색 요청은 캐시를 타면 안 된다는 요구사항이
있다. 전역 설정을 요청마다 임시로 몽키패치하는 방식은 asyncio 동시성 하에서 레이스
컨디션이 생겨 이미 검토 후 채택하지 않기로 결론 내렸다. 합의된 방향은 모듈 레벨 훅
(예: `set_cache_gate(fn: Callable[[list[str]], bool] | None)`)을 두고, lookup/store를
감싸는 데코레이터가 "cache_cfg.enabled and (훅이 없거나 훅(kb_ids)==True)"일 때만 실제로
캐시를 사용하도록 하는 것이다. 훅은 순수 함수 호출(요청마다 kb_ids만 보고 판단)이라
전역 mutable state 레이스 문제가 없다. rag-api 자체는 훅을 등록하지 않으므로(훅이
None), 이 patch가 rag-api 단독 동작을 전혀 바꾸지 않는다는 것이 핵심 요구사항이다 —
기존 캐시 동작, 로그 메시지, cache_status(hit/miss/disabled) 값 등이 훅 미등록 상태에서
100% 동일해야 한다. rag-ent-api 쪽에서 실제로 훅을 등록해 쓰는 것은 이 spec의 범위가
아니다 — 이 spec은 rag-api에 훅 등록 지점 + 데코레이터 리팩터링만 추가하는 것으로
범위를 한정한다.

## 목적

rag-ent-api처럼 rag-api를 in-process로 호출하는 외부 소비자가, rag-api 자체에는 없는
개념(KB의 public/private 구분)을 근거로 캐시 사용 여부를 요청 단위로 제어할 수 있게
하기 위함이다. 동시에 이 제어 지점이 rag-api 자체의 기존 캐시 동작에는 어떠한 영향도
주지 않아야 한다.

## 세부 기능 및 완료 기준

### F1. 캐시 게이트 훅 등록/해제

외부에서 kb_ids를 근거로 캐시 사용 여부를 판단하는 훅을 등록/해제할 수 있다.

- [ ] **F1-1**: 훅을 등록하지 않은 상태(초기 상태)에서는 캐시 사용 여부가 오직
  `cache_cfg.enabled` 값에만 좌우된다(훅이 있는 것처럼 캐시를 막는 동작이 발생하지
  않는다).
- [ ] **F1-2**: 훅을 등록한 뒤 그 훅이 특정 kb_ids 조합에 대해 거짓을 반환하면, 그 요청은
  `cache_cfg.enabled` 값과 무관하게 캐시 조회와 저장이 모두 수행되지 않는다.
- [ ] **F1-3**: 훅을 등록한 뒤 그 훅이 특정 kb_ids 조합에 대해 참을 반환하면, 그 요청은
  `cache_cfg.enabled`가 참일 때 훅 등록 이전과 동일하게 캐시 조회/저장이 수행된다.
- [ ] **F1-4**: 등록돼 있던 훅을 다시 없음 상태로 되돌리면, 이후 모든 요청이 F1-1과 동일한
  (훅 미등록) 동작으로 돌아간다.

### F2. lookup/store 캐시 사용 여부 판단 로직 통합

캐시 조회(lookup)와 저장(store) 각각에 대해 "실제로 캐시를 쓸지" 판단하는 로직이 한
곳에 모여 있고, 두 동작 모두 동일한 판단 결과를 따른다.

- [ ] **F2-1**: 동일한 요청(같은 kb_ids, 같은 `cache_cfg.enabled` 상태, 같은 훅 등록
  상태)에 대해 조회 시점의 캐시 사용 여부 판단과 저장 시점의 판단이 항상 일치한다 —
  조회는 막혔는데 저장은 되는(또는 그 반대) 상황이 발생하지 않는다.

### F3. 기존(훅 미등록) 동작 완전 보존

rag-api 자체는 훅을 등록하지 않으므로, 이 변경 이후에도 rag-api 단독 실행 시 캐시
관련 동작이 이 작업 이전과 관찰 가능한 수준에서 100% 동일하다.

- [ ] **F3-1**: 훅을 등록하지 않은 상태에서, 캐시 활성화(`cache_cfg.enabled=true`) 시
  exact/semantic 각 매칭 모드의 hit/miss 판정 결과와 응답 내용이 이 작업 이전과
  동일하다.
- [ ] **F3-2**: 훅을 등록하지 않은 상태에서, 캐시 비활성화(`cache_cfg.enabled=false`)
  시 캐시 조회/저장이 전혀 수행되지 않는다(이 작업 이전과 동일).
- [ ] **F3-3**: 훅을 등록하지 않은 상태에서, `/api/search` 응답의 `meta.cache_status`
  값(hit/miss/disabled)이 각 시나리오에서 이 작업 이전과 동일하게 나온다.
- [ ] **F3-4**: 훅을 등록하지 않은 상태에서, 캐시 hit/miss/store 시 남기는 로그 메시지
  내용이 이 작업 이전과 동일하다.
- [ ] **F3-5**: US-53/US-54에서 작성된 기존 검색 캐시 관련 테스트가 이 작업 이후에도
  (필요한 최소 수정만 거쳐) 모두 통과한다.

### 공통 완료 기준

- [ ] **C1**: 관련 테스트 전체 통과.

## 비범위

- rag-ent-api 쪽에서 실제로 캐시 게이트 훅을 등록해 public/private KB 판단 로직을
  구현하는 것 — 별도 프로젝트(rag-ent-api)의 작업이며 이 US의 범위가 아니다.
- 훅을 여러 개 동시에 등록/체이닝하는 기능 — 필요해지면 별도 US로 분리한다.
- KB의 public/private 같은 개념을 rag-api 자체 도메인 모델에 추가하는 것 — rag-api는
  이 개념을 모르는 채로 유지된다.

## 의존성

- US-53(검색 응답 캐싱), US-54(search_cache 설정 retrieval.cache 이동) — 이 두 작업으로
  만들어진 `search_cache` 모듈과 `retrieval.cache` 설정 위에서 진행된다.

## 오픈 이슈

- 캐시 게이트 훅 함수 자체가 예외를 던질 경우의 처리 방침(캐시 미사용으로 fail-safe
  폴백할지, 예외를 그대로 전파할지)이 요청 원문/배경 설명에 명시돼 있지 않다. design
  단계에서 정하되, rag-api 자체는 훅을 등록하지 않으므로 F3(기존 동작 보존)에는 영향을
  주지 않는다.
