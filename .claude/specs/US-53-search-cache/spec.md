## 목적

동일하거나 반복되는 검색 질의에 대해 매번 임베딩 생성·하이브리드 검색·리랭킹(Jina API 호출)
전체 파이프라인을 재실행하는 비용(레이턴시, 외부 리랭크 API 호출 비용)을 줄이기 위해, `POST
/api/search`의 최종 응답(리랭크까지 끝난 결과)을 캐싱한다. 이를 위해 기존 "저장소 역할
분리"(Redis는 인제스트/삭제 큐 전용) 원칙을 이번 US에서 의도적으로 깨고 Redis를 큐+캐시
겸용으로 확장한다.

## 세부 기능 및 완료 기준

### F1. Redis 캐시 설정값 도입

TTL과 최대 엔트리 수를 설정 가능하게 하여 캐시가 무한정 쌓이지 않도록 한다.

- [x] **F1-1**: `Settings`에 검색 캐시 설정 그룹(`enabled`/`ttl_seconds`/`max_entries`/
      `match_mode`(`exact`|`semantic`)/`semantic_threshold` 이상)이 추가되고 `settings.yaml`에서
      값을 오버라이드할 수 있다. 기본값은 `enabled=false`, `ttl_seconds=3600`,
      `max_entries=1000`, `match_mode=exact`, `semantic_threshold=0.95`(시맨틱 매칭도 기본
      비활성) — 단위 테스트(기본값 로드 확인 + override 값 로드 확인)
- [x] **F1-2**: 캐시가 비활성화(`enabled=false`)되어 있으면 캐시 조회/저장 로직이 완전히
      우회되어 매 요청이 항상 실제 검색·리랭크를 수행한다 — 단위 테스트
- [x] **F1-3**: 설정된 `ttl_seconds`(기본 3600초) 경과 후 캐시 엔트리가 자동 만료되어 이후
      동일 요청은 다시 실제 검색을 수행한다 — 단위 테스트(TTL을 짧게 설정하거나 Redis EXPIRE
      호출 인자를 mock으로 검증)
- [x] **F1-4**: 설정된 `max_entries`(기본 1000)를 초과하면 캐시 엔트리가 무한정 누적되지 않고
      정리된다(구체적 축출 정책은 design.md에서 결정) — 단위 테스트(엔트리 수 상한 초과
      시나리오)

### F2. 큐/캐시 Redis 키 네임스페이스 분리

기존 인제스트/삭제 큐(`rag:upload:queue`, `rag:delete:queue`, `rag:upload:delay`,
`rag:delete:delay` — `src/rag_api/pipeline/queue/enqueue.py`)와 캐시 엔트리가 같은 Redis 키
공간에서 충돌하지 않아야 한다.

- [x] **F2-1**: 캐시 키가 기존 큐 키들과 겹치지 않는 별도 prefix(또는 별도 Redis DB index)를
      사용한다 — 단위 테스트로 캐시 키 패턴이 기존 큐 키 프리픽스(`rag:upload:*`,
      `rag:delete:*`)와 겹치지 않음을 확인
- [x] **F2-2**: 캐시 기능 추가 후에도 기존 인제스트/삭제 큐 동작(push/pop/delay)에 회귀가
      없다 — 기존 큐 관련 테스트 전체 통과

### F3. 캐시 키 및 저장 값 정의 (exact/semantic 매칭)

"동일 질문"을 판단하는 기준과 캐시에 저장되는 값의 구조를 정의한다. 기본 매칭은 질의 문자열
정확 일치(exact)이며, 설정으로 켜면 임베딩 유사도 기반 시맨틱 매칭을 추가로 지원한다.

- [x] **F3-1**: 동일 `query` 문자열 + 동일 `kb_ids` 집합(순서 무관하게 동일 집합이면 동일
      취급) + 동일한 유효 검색 옵션(`mode`, `top_k`, `hybrid.alpha`, `hybrid.merge_strategy`,
      `similarity.min_score`, `rerank.enabled`, `rerank.top_n` — 요청 값과 settings 기본값이
      병합된 최종 유효값 기준)의 조합에 대해서만 캐시 hit이 발생한다 — 단위 테스트(쿼리는
      동일하고 옵션 중 하나만 다른 요청들이 각각 캐시 miss로 처리됨을 확인)
- [x] **F3-2**: `kb_ids`의 순서만 다른 두 요청은 동일 캐시 엔트리를 공유한다(hit) — 단위 테스트
- [x] **F3-3**: 캐시에는 리랭킹까지 완료된 최종 `SearchResponse`(query/results/meta) 전체가
      저장되고, 캐시 hit 시 실제 검색(retriever)·리랭크 호출 없이 저장된 값을 그대로 반환한다
      — 단위 테스트(캐시 hit 경로에서 retriever/reranker 호출이 발생하지 않음을 mock으로 확인)
- [x] **F3-4**: 캐시 hit/miss 여부를 API 응답에서 구분할 수 있도록 `SearchMeta`에 캐시 상태
      필드가 추가된다 — 단위 테스트(hit/miss 각 케이스에서 해당 필드 값 확인)
- [x] **F3-5**: `match_mode=semantic`이고 동일 `kb_ids`/검색 옵션 조합에서, 질의 임베딩과 기존
      캐시 엔트리 질의 임베딩의 코사인 유사도가 `semantic_threshold` 이상이면 문자열이 달라도
      캐시 hit이 발생한다 — 단위 테스트(유사도가 임계값 이상/미만인 두 쌍 각각 hit/miss 확인).
      질의 임베딩은 검색 파이프라인에서 이미 생성하는 임베딩을 재사용하고 별도로 재생성하지
      않는다.
- [x] **F3-6**: `match_mode=exact`(기본값)에서는 시맨틱 유사도 비교 로직이 전혀 실행되지
      않고 F3-1~F3-4의 정확 일치 동작만 수행된다 — 단위 테스트(기본 설정 상태에서 유사하지만
      다른 질의가 miss로 처리됨을 확인)

### F4. KB 문서 변경/삭제 시 캐시 자동 무효화

**결론**: 필요하다. 캐시 대상이 검색 결과 전체이므로, 대상 KB의 문서가 추가/재인덱싱/삭제되면
캐시된 응답이 새 문서를 반영하지 못하는 정합성 문제가 생긴다. TTL만으로는 그 사이 기간 동안
오래된 결과가 계속 반환되므로, 문서 상태 변화 시점에 맞춰 즉시 무효화한다.

- [x] **F4-1**: 문서가 `indexed` 상태로 전이(신규 인제스트 또는 재인덱싱 완료)되면 해당
      `kb_id`가 포함된 모든 캐시 엔트리(다중 KB 조합 캐시 포함)가 무효화된다 — 단위 테스트
- [x] **F4-2**: 문서 삭제(soft/hard 불문)가 완료되면 해당 `kb_id`가 포함된 모든 캐시
      엔트리가 무효화된다 — 단위 테스트
- [x] **F4-3**: KB 자체가 삭제되면 해당 `kb_id`가 포함된 모든 캐시 엔트리가 무효화된다 —
      단위 테스트

### F5. 캐시 수동 클리어 API

**결론**: 필요하다. F4의 자동 무효화는 문서 상태 전이 이벤트에 연동되므로, 그 경로를 거치지
않는 예외적 운영 상황(예: 캐시 로직 자체의 이상 동작 의심, 운영자의 즉시 초기화 필요, 이번
범위 밖의 원인으로 Qdrant/Postgres 데이터가 파이프라인 밖에서 직접 변경된 경우)에는 TTL
만료까지 기다리지 않고 강제로 비울 수단이 필요하다. (참고: 검색 옵션 값 자체가 캐시 키에
포함되므로, KB 설정 오버라이드 변경처럼 옵션의 유효값이 바뀌는 경우는 새 키로 자동
분리되어 별도 무효화 로직 없이도 정합성이 유지된다 — 이 케이스는 수동 클리어가 필요한
이유에서 제외한다.)

- [x] **F5-1**: 특정 `kb_id`가 포함된 캐시를 강제로 비우는 API가 있다 — 단위/통합
      테스트(호출 후 이전에 캐시 hit이던 요청이 miss로 바뀜을 확인)
- [x] **F5-2**: 전체 검색 캐시를 강제로 비우는 API(또는 파라미터)가 있다 — 단위/통합 테스트
- [x] **F5-3**: 캐시가 비어 있거나 캐시 기능 자체가 비활성 상태에서 클리어 API를 호출해도
      에러 없이 정상 처리된다 — 단위 테스트

## 비범위

- 검색 파이프라인 중간 산물(임베딩, 리랭킹 전 원시 후보 목록) 캐싱 — 캐시 대상은 확정된 대로
  "리랭크까지 끝난 최종 응답 전체"로 한정한다.
- 캐시 히트율 등 캐시 전용 모니터링 지표/대시보드 노출 — 필요하면 별도 US로 분리한다.
- 다중 API 인스턴스 간 캐시 무효화 전파를 위한 pub/sub 등 별도 메커니즘 — Redis를 여러
  인스턴스가 이미 공유하므로 이번 범위의 구현(F4/F5)만으로 자연히 공유되며, 그 이상의
  최적화는 다루지 않는다.
- `src/rag_api/infra/CLAUDE.md`가 언급하는, 실제 코드에는 없는 "ETag 캐시" 키 컨벤션 정리 —
  이번 US와 무관한 기존 문서 불일치이며 별도로 정리한다 (아래 오픈 이슈 참고).

## 의존성

- 없음. Redis 클라이언트(`src/rag_api/infra/redis.py`)와 검색 API(`src/rag_api/api/routers/

## 오픈 이슈 (선택)

- `src/rag_api/infra/CLAUDE.md`에 실제로 구현되지 않은 "ETag 캐시" 키 컨벤션
  (`etag:{kb_id}:{doc_source}`)이 문서화되어 있어 코드와 불일치한다. 이번 US 판단 근거로
  쓰지 않았으며, US-53 범위와 무관하게 별도로 정리가 필요하다.
- `ttl_seconds`(기본 3600)·`max_entries`(기본 1000)는 F1-1에서 확정했으나, F1-4의 구체적
  축출 정책(LRU/FIFO 등)은 이번 spec에서 확정하지 않았다 — design.md에서 결정한다.
- `semantic_threshold`는 F1-1에서 기본 0.95(보수적 값)로 확정했으나, 시맨틱 매칭용 질의
  임베딩 유사도 검색을 어디서 수행할지(예: 소규모 전용 Qdrant 컬렉션 vs 다른 방식)는 이번
  spec에서 확정하지 않았다 — design.md에서 결정한다. `match_mode=semantic`이 오탐(의도가
  다른 질문을 같은 캐시로 처리)을 유발할 수 있다는 점은 design.md에서 추가 완화 방안과 함께
  다룬다.
