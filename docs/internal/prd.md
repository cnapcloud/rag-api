# RAG API 요구사항

> 문서 인제스트 및 하이브리드 검색 파이프라인의 기능 요구사항 정의.
> 구현 방식은 [architecture.md](architecture.md), API 명세는 [api-spec.md](api-spec.md) 참고.

---

## 1. Knowledge Base 관리

- KB(Knowledge Base)는 독립적인 문서 집합 단위이다.
- KB는 설정 파일(`settings.yaml`) 또는 API를 통해 생성할 수 있다.
- KB별로 문서, 벡터 인덱스, 메타데이터가 완전히 분리되어 관리된다.
- KB 삭제 시 해당 KB의 모든 문서, 벡터, 메타데이터가 함께 삭제된다.

---

## 2. 문서 인제스트

인제스트(Ingest)란 업로드된 문서를 파싱·청킹·임베딩하여 검색 가능한 형태로 벡터 DB에 저장하는 전처리 과정이다.

### 지원 파일 형식

- PDF, Markdown, DOCX, TXT, HWP

### 업로드

- 단일 파일 업로드와 배치(다중 파일) 업로드를 모두 지원한다.
- 업로드 즉시 인제스트 파이프라인이 비동기로 시작된다.

### 파이프라인 단계

1. **검증**: 파일 크기 제한 초과 여부 확인. ETag 기반 중복 여부 확인.
2. **파싱**: 파일 형식에 맞는 리더로 텍스트 추출.
3. **청킹**: 설정된 전략(recursive / semantic / document_aware)으로 청크 분할.
4. **임베딩**: Dense 벡터(bge-m3 등) + Sparse 벡터(BM25)를 병렬 생성.
5. **저장**: 기존 청크 삭제 후 새 청크를 벡터 DB에 저장.
6. **메타데이터 갱신**: 처리 상태, 청크 수, 인덱싱 시각 등을 기록.

### 재업로드 처리

- 내용이 변경되지 않은 문서를 재업로드하면 인제스트를 건너뛰고 기존 인덱스를 유지한다.
- 내용이 변경된 문서를 재업로드하면 기존 인덱스를 새 내용으로 교체한다.
- 인제스트 또는 삭제가 진행 중인 문서는 해당 작업 완료 후 재업로드가 처리된다.
- 강제 재인덱싱 옵션을 지정하면 변경 여부와 관계없이 재인제스트한다.

### 문서 삭제

- 문서를 삭제하면 해당 문서의 인덱스와 모든 관련 데이터가 자동으로 함께 제거된다.

### 파일 크기 제한

- 최대 허용 파일 크기를 설정으로 관리한다 (기본 200MB).
- 초과 시 인제스트를 거부하고 실패 상태로 기록한다.

---

## 3. 문서 상태 관리

- 각 문서는 처리 상태를 실시간으로 추적한다.
- 상태 값: `running` | `indexed` | `failed` | `deleting`
- 실패 시 오류 메시지와 함께 `failed` 상태로 기록된다.
- 문서 상태는 API를 통해 조회할 수 있다.

---

## 4. 동시성 제어

### 동일 문서 — 인제스트와 삭제 관계

- 동일 문서에 대한 인제스트와 삭제는 동시에 실행될 수 없다.
- 인제스트가 진행 중인 문서에 삭제 요청이 들어오면, 인제스트 완료 후 삭제가 실행된다.
- 삭제가 진행 중인 문서에 인제스트 요청이 들어오면, 삭제 완료 후 인제스트가 실행된다.

### 다중 문서 병렬 처리

- 서로 다른 문서는 동시에 인제스트할 수 있다.
- 동시에 처리할 수 있는 최대 문서 수는 설정으로 제한한다.

---

## 5. Stuck 문서 자동 복구

- 서버 비정상 종료 등으로 인해 `running` 상태에 고착된(zombie) 문서를 감지할 수 있다.
- 동일 문서의 재업로드 시점에 이전 작업이 더 이상 활성 상태가 아님이 확인되면 자동으로 `failed`로 전환하고 새 처리를 시작한다.
- 수동 복구 API를 통해 `running` 상태의 문서를 즉시 `failed`로 전환하고 재처리를 시작할 수 있다.

---

## 6. 하이브리드 검색

- Dense 벡터(의미 기반)와 Sparse 벡터(키워드 기반) 검색을 결합한 하이브리드 검색을 제공한다.
- Dense/Sparse 가중치(`alpha`)를 요청 시 조정할 수 있다.
- 복수의 KB에 대해 동시에 검색하고 결과를 통합할 수 있다.
- 복수 KB 검색 결과는 RRF(Reciprocal Rank Fusion)로 순위를 통합한다.

---

## 7. 리랭킹

- 검색 후보 결과에 대해 리랭커 API(Jina, Cohere, Voyage 등)를 이용한 정밀 재순위를 수행한다.
- 리랭커 API 호출 실패 시 RRF 점수 기반 순위를 fallback으로 사용한다.
- 리랭킹 활성화 여부, 최종 반환 개수(top_n), 타임아웃을 설정으로 관리한다.

---

## 8. 헬스체크

- **Liveness** (`/health`): 서버 프로세스 생존 여부 확인.
- **Readiness** (`/ready`): 연결된 모든 인프라(벡터 DB, 캐시, 오브젝트 스토리지, 임베딩 서버)의 정상 여부 확인. 하나라도 불가 시 503 반환.

---

## 9. 운영

- 인제스트 파이프라인은 Dagster(기본) 또는 경량 QueueWorker 중 설정으로 선택할 수 있다.
- 모든 설정 값(파일 크기 제한, 청킹 전략, 임베딩 모델, 동시성 등)은 코드 변경 없이 설정 파일로 관리한다.
- 문서 전체 현황(KB별, 상태별)을 단일 API로 조회할 수 있다.
- 특정 KB 또는 개별 문서를 강제 재인덱싱할 수 있다.

---

## 10. 중복 문서 감지 (Dedup)

- 신규 문서 인제스트 시 동일 KB 내 기존 문서와 유사도를 자동으로 비교한다.
- 비교는 비용 오름차순으로 단계적으로 수행한다: 해시 비교 → MinHash 밴드 비교 → 벡터 유사도.
- 판정 결과는 동일(identical), 제목변경(title_changed), 유사(similar), 무관(none)으로 분류한다.

### 판정별 처리

- **동일**: 신규 문서를 `outdated`로 마킹하고 인제스트를 건너뛴다.
- **제목변경(본문 동일)**: 신규가 더 최신이면 기존 문서를 `outdated`로 전환하고 Qdrant payload를 새 제목으로 갱신한다. 신규가 더 오래됐으면 신규를 `outdated`로 마킹한다.
- **유사**: 더 최신인 문서가 인덱스를 차지한다. 기존이 더 오래됐으면 기존 Qdrant 청크를 삭제하고 `outdated`로 전환한 뒤 신규를 인덱싱한다. 신규가 더 오래됐으면 신규를 `outdated`로 마킹하고 인제스트를 건너뛴다.
- **무관**: 일반 인제스트를 진행한다.

### outdated 문서 처리

- `outdated` 상태가 된 문서의 dedup 밴드(simhash_bands, minhash_bands)는 즉시 삭제한다.
- `outdated` 문서의 Qdrant 청크는 판정 유형에 따라 삭제 여부가 결정된다(동일/제목변경은 유지, 유사는 삭제).

---

## 11. 커넥터 (Connector)

- 외부 소스(GitHub 레포지토리, Confluence 페이지, Web URL)에서 문서를 가져와 인제스트 파이프라인에 투입할 수 있다.
- 커넥터별로 대상 소스, 인증 정보, 동기화 스케줄을 독립적으로 설정한다.
- 인증 토큰 등 민감 정보는 암호화하여 저장하고, API 응답에는 마스킹하여 반환한다.

### 동기화

- 수동 sync API를 통해 즉시 동기화를 트리거할 수 있다.
- cron 표현식으로 자동 동기화 스케줄을 설정할 수 있다.
- 동기화 중에는 `sync_status=running`으로 표시되며, 완료 후 `idle`로 복귀한다.
- 동기화 중 오류 발생 시 커넥터 상태를 `error`로 기록하고 계속 진행 가능한 경우 나머지 파일을 처리한다.

### 운영 액션

- **Pause**: 수동/자동 동기화를 전면 차단한다.
- **Resume**: pause 상태를 해제하고 정상 운영으로 복귀한다.
- **Reset**: `sync_status`가 stuck된 경우 `idle`로 강제 초기화한다. 실행 중인 작업을 중단하지는 않는다.

### 문서 관리

- 동일 소스 URI의 문서가 이미 존재하면 재인제스트(갱신)하고, 없으면 신규 문서로 등록한다.
- 커넥터로 가져온 문서는 일반 문서와 동일하게 dedup, 인제스트, 삭제 파이프라인을 거친다.
