# Web 커넥터 처리 구조

> 요건: [prd.md §11](../requirement/prd.md#11-커넥터-connector) "커넥터(Connector)" — Web 소스(R-09)

## 1. 개요

`WebConnector`(`src/rag_api/connectors/web.py`)는 seed URL에서 시작해 BFS로 페이지를 순회하며,
각 페이지를 HTML 문서로 스테이징하는 커넥터다. 다른 커넥터(GitHub/Confluence)와 달리 대상
서버가 협조적인 API를 제공하지 않는다는 전제 — "변경 여부를 물어볼 수 있는 API가 없고, 사이트
구조를 신뢰할 수 없다" — 가 이 문서 전체를 관통하는 제약이다. 커넥터 공통 흐름(Flow B)은
[multi-source-ingest.md §2](multi-source-ingest.md) 참고, 이 문서는 Web 커넥터 고유의 크롤링·
변경 감지·콘텐츠 추출 상호작용만 다룬다.

관련 문서:
- [html-extraction.md](html-extraction.md) — trafilatura 추출 정책(`html_extraction_policy`) 자체의 설계
- [dedup.md](dedup.md) — 이 문서 4절에서 다루는 dedup 오탐이 어느 단계에서 확정되는지
- [connector-state-flow.md](connector-state-flow.md) — sync 상태 전이, abort
- `docs/internal/known-issues.md` #18/#19/#20 — 이 문서에서 설명하는 각 한계의 발견 경위·실측값

## 2. BFS 크롤링 범위

seed URL마다 두 가지 스코프 모드 중 하나로 크롤링 범위가 정해진다.

| 모드 | 판단 기준 | 예 |
|---|---|---|
| 경로 제한 (기본) | seed URL의 경로 prefix 아래만 허용 | seed가 `.../docs/api`면 `.../docs/api/*`만 허용, `.../docs/guide`는 제외 |
| `unrestricted: true` | seed와 같은 도메인이면 경로 무관하게 허용 | seed가 `.../w/고양이`여도 같은 도메인의 `.../random`, `.../RecentChanges`까지 허용 |

`exclude_patterns`(fnmatch)는 두 모드 모두에서 최우선으로 적용되어 스코프를 통과한 URL도 걸러낼
수 있다. `include_patterns`는 스코프 통과 후 추가로 좁히는 필터다. `depth`는 seed로부터의 BFS
홉 수 상한, `max_pages`는 한 sync당 처리할 페이지 수 상한이다(발견된 링크가 이보다 많아도 큐
크기는 `max_pages`의 20배에서 잘라 메모리 폭증을 막는다).

**실측 사례** (namu.wiki "고양이", `unrestricted: true`, `depth: 1`): seed 페이지에서 시작한
크롤이 `/w/고양이` 본문뿐 아니라 사이트 전역 네비게이션에 걸려있는 `/random`, `/RecentChanges`,
`/RecentDiscuss`, `/`(메인)까지 끌어왔다. `unrestricted`는 "seed와 관련된 문서를 넓게 모으고
싶다"는 의도(예: 카테고리로 연결된 관련 동물 문서들)로 켜는 옵션이지만, 그 대가로 사이트 공통
유틸리티 링크까지 스코프에 들어온다 — 3.3절 참고.

## 3. 페이지 처리 파이프라인

한 페이지가 fetch된 뒤 스테이징까지 가는 경로는 아래 순서로 필터링된다. 앞 단계에서 걸러지면
뒤 단계(변경 감지, S3 업로드, enqueue)는 실행되지 않지만, 링크 발견(BFS 확장)을 위해 HTML 자체는
항상 반환된다.

```
httpx GET(source_uri)
    │
    ▼
content-type이 text/html인가?  ── 아니오 → 중단(링크 발견도 안 함)
    │ 예
    ▼
depth==0 이면서 skip_seed_pages=true?  ── 예 → 스테이징 스킵(링크 발견만)
    │ 아니오
    ▼
페이지네이션 URL인가? (/page/2/, ?page=3)  ── 예 → 스테이징 스킵(링크 발견만)
    │ 아니오
    ▼
trafilatura 추출 결과 길이 >= min_content_chars?  ── 아니오 → 스테이징 스킵(링크 발견만)
    │ 예
    ▼
변경 감지 (4절) — 동일 문서로 판단?  ── 예 → 메타데이터만 갱신, 스테이징 스킵
    │ 아니오(신규/변경)
    ▼
S3 스테이징 → Postgres content_version 갱신 → 인제스트 이벤트 enqueue
```

seed 페이지(depth 0)와 페이지네이션 인덱스 페이지는 "링크를 찾기 위해 방문은 하지만 검색
대상 문서로 취급하지 않는" 동일한 패턴을 공유한다 — 목차/색인 성격의 페이지이기 때문.

## 4. 변경 감지 — ETag와 콘텐츠 해시 폴백

### 4.1 기본: HTTP ETag

서버가 `ETag` 응답 헤더를 보내면 이 값을 그대로 `content_version`으로 저장하고, 다음 sync에서
동일 값이면 "변경 없음"으로 스킵한다. GitHub/Confluence 커넥터는 API가 보장하는 버전 식별자
(blob SHA, 페이지 버전 번호)를 쓰지만, Web 커넥터는 임의 서버의 HTTP 헤더에 의존한다는 점에서
근본적으로 신뢰도가 낮다.

### 4.2 ETag 미제공 시 폴백 — 왜 raw HTML 해시로는 안 됐는가

많은 사이트가 HTML 응답에 `ETag`를 아예 안 보낸다. 최초 구현은 이 경우 raw HTML 전체를 MD5
해싱해 대신 썼는데, 이는 실제로는 작동하지 않았다 — namu.wiki 페이지를 연속 두 번 fetch해
검증한 결과:

| 비교 대상 | 결과 |
|---|---|
| raw HTML MD5 | 매 요청마다 다름 |
| trafilatura 추출 텍스트 MD5 | 동일 |

원인은 페이지 안에 `<script>window.INITIAL_STATE="..."</script>` 형태로 요청마다 내용이
랜덤하게 바뀌는 대용량 인코딩 블롭이 박혀있기 때문이다(길이는 고정, 바이트는 매번 다름 —
스크래핑 방지 목적으로 추정). 이 블롭이 raw HTML 안에 있는 한, 실제 문서 내용이 그대로여도
전체 해시는 항상 달라진다.

### 4.3 현재: 추출 텍스트 해싱

그래서 ETag가 없을 때는 raw HTML이 아니라 trafilatura로 추출한 본문 텍스트를 해싱한다(추출
실패 시에만 raw HTML 해시로 재폴백). `<script>` 블록은 추출 결과에 애초에 포함되지 않으므로
이 문제를 피해간다. 단, 이 폴백은 "추출된 텍스트가 실제로 페이지 고유의 콘텐츠를 대표한다"는
전제 위에 서 있고, 이 전제가 깨지는 경우가 5절이다.

## 5. 알려진 구조적 한계

### 5.1 원천적으로 매번 바뀌는 페이지 — 유틸리티/동적 엔드포인트

일부 URL은 이름 그대로 요청마다 다른 내용을 보여주도록 설계되어 있다 — "무작위 문서",
"최근 변경", "최근 토론" 같은 목록. 이런 페이지는 raw HTML 해시든 추출 텍스트 해시든 어떤
전략을 쓰더라도 "변경 없음" 판정이 원천적으로 불가능하다(실제 표시 내용 자체가 매번
다르므로). `unrestricted: true`로 크롤링 범위를 넓히면 2절에서 설명한 사이트 전역 네비게이션
경유로 이런 페이지가 크롤 대상에 섞여 들어올 수 있다. 유일한 대응은 `exclude_patterns`로
크롤링 단계에서 아예 제외하는 것 — 콘텐츠 해싱으로는 해결할 수 없는 범주다.

### 5.2 목록형/카테고리 페이지 — 추출 자체가 실제 콘텐츠를 다 지워버림

카테고리·색인 페이지는 본문이 프로즈(문단) 대신 순수 링크 목록(`제목 → 링크`가 반복되는
구조)으로 이루어진다. trafilatura를 비롯한 밀도 기반 추출기는 "한 블록의 텍스트 중 링크 텍스트
비율이 높으면 내비게이션/보일러플레이트로 간주해 삭제"하는 휴리스틱을 쓰는데, 카테고리 페이지의
링크 목록은 이 조건에 정확히 들어맞아 통째로 삭제된다. 이 판정은 추출 정책(`strict`/`lenient`/
`balanced`, [html-extraction.md §3.2](html-extraction.md)) 설정과 무관하게 적용된다 — 정책이
조절하는 건 "애매한 블록을 얼마나 적극적으로 포함시킬지"이지, "링크 비율이 압도적으로 높은
블록을 지울지 말지"의 판단 자체가 아니기 때문이다.

**실측 사례**: namu.wiki의 "분류:고양이"와 "분류:생태계교란 생물" — 서로 무관한 두 카테고리 —
를 추출하면 둘 다 카테고리 소속 문서 목록은 사라지고, 사이트 전체에 동일하게 박혀있는 저작권
고지 문단(약 400~600자)만 남는다. 이 남은 텍스트는 두 페이지에서 사실상 동일하므로:

- 4.3절의 콘텐츠 해시가 사실상 같은 값이 되어 서로 다른 문서를 "동일 문서"로 오판할 위험이 있고
- 실제 관찰된 결과는 dedup 파이프라인 3단계(`chunk_compare`, [dedup.md](dedup.md))에서
  나타났다 — 추출된 텍스트가 짧아 각 문서가 청크 1개로 압축됐고, 그 유일한 청크(=공통 저작권
  문단)끼리 코사인 유사도 0.969로 계산되어 "생태계교란 생물" 문서가 "고양이" 문서의 중복으로
  판정(`status=outdated`)됐다.

이 경우 dedup 로직 자체는 정상 동작한 것이고, 원인은 그 앞단인 추출 단계에서 두 문서가 이미
"거의 빈 문서 + 동일한 공통 푸터"로 축소되어 있었다는 데 있다. 카테고리/목록형 페이지를
`exclude_patterns`로 제외하는 것이 가장 확실한 대응이며, 애초에 목록 페이지는 본문 검색
대상으로서의 가치도 낮다.

## 6. 오픈 이슈

- 5.1/5.2 모두 근본 해결책은 "크롤링하지 않기"(`exclude_patterns`)뿐이며, 사이트별로 운영자가
  수동으로 채워야 한다. URL 패턴만으로 유틸리티/목록형 페이지를 자동 판별하는 범용적인 방법은
  없음.
- 5.2의 "링크 밀집 블록 삭제" 휴리스틱을 목록형 페이지에서 우회하는 별도 파서(예: 링크
  텍스트만 모아 목록으로 취급)는 검토되지 않았다 — 카테고리 페이지 자체를 색인 대상으로 삼을
  실익이 있는지부터 확인 필요.
- `_has_sufficient_content()`(3절의 충분성 게이트)가 항상 중립(`balanced`) 정책으로 trafilatura를
  호출해, 실제 파싱 단계(`lenient`, [html-extraction.md](html-extraction.md))와 게이팅 기준이
  다르다는 비일관성은 아직 해소되지 않음.

상세 발견 경위·실측 로그는 `docs/internal/known-issues.md` #18(4.2), #19(5.1), #20(5.2) 참고.

## 7. 정책별 실제 추출 결과 비교 (예시)

5.2절의 "분류:고양이" 페이지를 `strict`/`balanced`/`lenient` 세 정책으로 각각 재추출해 실측한
결과다. 원본 페이지에서 이 부분에 해당하는 실제 마크업 구조는 다음과 같다 — 카테고리 소속 문서
목록(링크 밀집)과, 사이트 어디서나 동일하게 나오는 저작권 안내 문단(프로즈)이 함께 있다.

```
<div>
  <h3>ㄱ</h3>
  <ul>
    <li><a href="/w/삼색묘">삼색묘</a></li>
    <li><a href="/w/코숏">코숏</a></li>
    ... (전체 61개 문서)
  </ul>
</div>
<p>이 저작물은 CC BY-NC-SA 2.0 KR에 따라 이용할 수 있습니다. ...</p>
```

세 정책으로 이 페이지를 재추출한 실제 결과:

| 정책 | 추출 길이 | 실제로 남은 내용 |
|---|---|---|
| `strict` | 251자 | 저작권 안내 문단만 |
| `balanced` | 431자 | 저작권 안내 문단 + reCAPTCHA/hCaptcha 고지 |
| `lenient` | 621자 | "전체 61개 문서"(개수 라벨 한 줄) + 저작권 안내 문단 + reCAPTCHA 고지 + 사이트 하단 네비게이션(Contáctenos, Términos de uso 등) |

세 정책 모두 카테고리 소속 문서 목록(삼색묘, 코숏, 러시안블루 ...) 자체는 **단 하나도 건지지
못한다.** `lenient`가 그나마 더 많이 남기지만, 남는 건 목록 바로 앞에 있던 "전체 61개 문서"라는
개수 라벨 한 줄뿐 — 그마저도 이 라벨이 `<ul>` 링크 목록 바깥의 별도 `<div>`라서 링크 밀집
판정을 피해간 우연이지, 목록 자체가 살아난 게 아니다. 즉 정책을 아무리 완화해도 이 페이지
유형에서는 "본문"이라고 부를 만한 내용이 사실상 복구되지 않는다 — 5.2절에서 설명한 한계가
정책 설정으로 우회되지 않음을 실측으로 보여준다.
